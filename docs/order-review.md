# Reviewed order creation

Ordinary creation opens a SERIALIZABLE transaction. The order controller explicitly requests serializable isolation through the internal sync mutation contract. Sync-wrapped creation sets SERIALIZABLE on its existing outer transaction before the first statement; it does not open a separate database session. The transaction snapshot is the linearization point. It covers the applicable shop settings, recipes and all linked cost sources, including ingredient-set predicates. A source change committed after that point can serialize after the accepted order and does not retroactively invalidate it. Shop pricing is loaded from that snapshot rather than trusted from actor context.

Selected recipe rows take KEY SHARE locks in recipe-ID order. These protect the gap between reading the recipe and inserting its foreign-key reference, without blocking ordinary non-key recipe edits. Missing or foreign-shop IDs expose only NOT_FOUND. Inactive/unverified recipes are retained in review state and excluded from candidate persisted lines. Stock quantity does not affect eligibility. The shared complete/partial provider supplies prices and costing provenance.

Before any invoice allocation, the review policy returns all price/availability conflicts together. Confirmed exclusions work only while those IDs remain unavailable; reappearance requires review. No available items fails with NO_AVAILABLE_ITEMS. Malformed yields and nonfinite, negative or storage-overflow source prices fail recoverably without exposing invalid review-price strings; aggregate amounts outside the existing storage range fail before writes. Existing historical records are not recalculated.

Only SQLSTATE 40001 or 40P01 restarts the entire owning transaction, at most 12 attempts. The original three-attempt proposal failed the existing 10-way numbering test (five temporary failures); 12 preserves that existing all-ten-success requirement without weakening its assertions. Connection failures, ambiguous commits and unique violations are not automatically retried. Every retry resets deferred success effects, including a retry that finds an already committed sync receipt. Audit/order-created effects run after commit; rollback emits no success event.

Operational questions: did creation retry, was review rejected, and did an order commit? Request-scoped order_create_retry / sync_transaction_retry (attempt), order_review_rejected (code), and existing order_created events answer these without logging customer text, addresses, prices or recipe names. Existing HTTP error handling reports exhausted transient database failures as retryable service unavailability.

Sources: [PostgreSQL isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [whole-transaction retry guidance](https://www.postgresql.org/docs/current/mvcc-serialization-failure-handling.html), [Drizzle transactions](https://orm.drizzle.team/docs/transactions). No new broad application lock or dependency is introduced. Code rollback restores previous creation behavior for subsequent requests; saved snapshots remain intact. Partial-line profit accounting is T16, and frontend workflow/caller retirement remains subsequent initiative work; coordinate the complete rollout before production deployment.


Verification includes 18 disposable-PostgreSQL scenarios covering ordinary and sync-wrapped shop races, ingredient price/link/insertion changes, shared general prices, recipe status/deactivation/deletion, exact sync replay, renewed review, malformed yield and foreign IDs. A test-only barrier pauses after source reads and before invoice allocation; no production test hook is introduced. Existing ten-way numbering, sync rollback/replay and order-transition regression tests remain required. The transition fixture includes the additive delivery-date column and fails fast if its read cannot reach the barrier.
